# release-promotion-agent

Агент готовит релизные изменения конфигурационных файлов и оформляет их
pull request'ами. Ручная работа инженера сопровождения при каждом релизе —
пройти по всем репозиториям контроллеров, сверить план установки с тем, что
реально изменилось в релизной ветке, поправить конфиги стендов и открыть
запросы на слияние. Агент делает эту работу под контролем человека.

Слияние и деплой агент не выполняет: он останавливается на открытом pull
request, дальше работает штатный процесс ревью и CI/CD.

## Как устроена работа

Агент опирается на два независимых источника и никогда их не смешивает:

| Источник | Что это | Откуда берётся |
|---|---|---|
| **Факт** | что действительно изменилось в релизе | diff релизной ветки к базовой |
| **Намерение** | что должно измениться по инструкции | план установки на странице релиза |

Расхождения между ними агент не решает сам — он их показывает человеку.

### Порядок сессии

```
параметры сессии
      │
      ├─► diff релизной ветки  ──────────┐
      │                                  ├─► сверка ──► расхождения
      └─► план установки релиза ─────────┘                  │
                                                            ▼
                                       модель предлагает изменения конфигов
                                                            │
                                                    проверка кандидатов
                                                            │
                                              ╔═════════════▼═════════════╗
                                              ║  чекпоинт 1: план         ║
                                              ╚═════════════╤═════════════╝
                                                            │ подтверждено
                          для каждого репозитория ◄─────────┘
                                    │
                       временная ветка → коммит → pull request
                                    │
                      ╔═════════════▼═════════════╗
                      ║  чекпоинт 2: pull request ║
                      ╚═════════════╤═════════════╝
                                    │ подтверждено
                            отчёт со ссылками на PR
```

До первого подтверждения человеком агент только читает: ни одной записи во
внешние системы не происходит.

### Разделение ролей

Языковая модель **предлагает** изменения, но не выполняет их. Ветки, коммиты
и pull request создаёт обычный код агента, и только после того, как человек
подтвердил план. У модели нет инструментов записи — есть только чтение diff,
инструкции, текущих конфигов и результатов проверки.

Проверка кандидатов тоже не поручена модели: корректность YAML и границы
допустимых правок проверяет отдельный код, который не зависит от кода,
порождающего эти правки.

### Границы правок

Каждая позиция плана несёт список ключей, которые разрешено менять. Если
кандидат тронул что-то ещё — например, уровень логирования, которого не было
в плане, — изменение отклоняется целиком, а не «почти проходит».

### Что происходит, когда что-то идёт не так

| Ситуация | Поведение |
|---|---|
| Кандидат не прошёл проверку | до трёх попыток, каждая с текстом прошлых ошибок |
| Одна и та же ошибка дважды подряд | остановка сразу, третья попытка не делается |
| Три разные неудачи подряд | остановка, работу продолжает человек |
| Модель недоступна | инженер получает исходный diff и инструкцию для ручной работы |
| Сбой сети или ошибка 5xx | три попытки с нарастающей паузой |
| Повторный проход по репозиторию | существующие ветка и PR переиспользуются |

## Структура кода

```
release_promotion_agent/
  agents/          оркестратор релизного сценария и диалоговый агент
  analyzers/       diff веток (факт), намерение, сверка
  validation/      проверка YAML и границ правок
  tools/           выходы во внешние системы: SourceControl, Confluence
  llm/             работа с языковой моделью
  prompts/         сборка системного промпта по частям
  models/          модели ответа и статистики диалога
  core/            автомат сессии, состояние, контекст, ошибки, аудит, логи
  cli/             командный интерфейс и демонстрационный прогон
  sberchat_bot/    интерфейс чат-бота
  config.py        конфигурация из переменных окружения
tests/             модульные и интеграционные тесты
```

Модули не вызывают друг друга напрямую: все связи идут через оркестратор.
Это проверяется линтером на каждом запуске, а не поддерживается вручную.

Состояние сессии живёт в памяти процесса: база данных не используется.

## Запуск без Docker

Нужен Python 3.11 или новее.

```bash
python -m venv .venv
```

```bash
.venv/Scripts/activate
```

На Linux и macOS активация выглядит так:

```bash
source .venv/bin/activate
```

Установка вместе с инструментами разработки:

```bash
pip install -e ".[dev]"
```

Демонстрационный прогон — проходит весь сценарий на подставных данных, к
сети не обращается:

```bash
release-promotion-agent demo
```

Тот же прогон, но с корректировками на обоих чекпоинтах:

```bash
release-promotion-agent demo --with-corrections
```

Проверка конфигурации перед работой с реальными системами:

```bash
release-promotion-agent check-config
```

Тесты и проверки кода:

```bash
pytest
```

```bash
ruff check . && ruff format --check . && lint-imports
```

## Запуск в Docker

Сборка образа:

```bash
docker build -t release-promotion-agent .
```

Если пакеты ставятся из внутреннего зеркала, индекс передаётся аргументом:

```bash
docker build --build-arg PIP_INDEX_URL=<адрес зеркала> -t release-promotion-agent .
```

Демонстрационный прогон в контейнере:

```bash
docker run --rm release-promotion-agent demo
```

Проверка конфигурации с передачей переменных окружения из файла:

```bash
docker run --rm --env-file .env release-promotion-agent check-config
```

Секреты передаются только переменными окружения при запуске и в образ не
попадают.

## Настройка

Скопируйте `.env.example` в `.env` и заполните значения. Файл `.env` в
репозиторий не попадает.

| Переменная | Назначение |
|---|---|
| `SOURCECONTROL_BASE_URL` | адрес API системы контроля версий |
| `SOURCECONTROL_TOKEN` | токен доступа; права на слияние не нужны |
| `CONFLUENCE_BASE_URL`, `CONFLUENCE_TOKEN` | доступ к странице релиза |
| `CONFLUENCE_CA_BUNDLE` | корневой сертификат внутреннего центра для проверки сервера Confluence |
| `CONFLUENCE_VERIFY_SSL` | проверка сертификата Confluence; по умолчанию включена |
| `GIGACHAT_CERT_FILE`, `GIGACHAT_KEY_FILE` | сертификат и ключ для доступа к модели |
| `GIGACHAT_KEY_FILE_PASSWORD` | пароль ключа, если он задан |
| `SBERCHAT_WEBHOOK_TOKEN` | уведомления в чат, необязательно |
| `AGENT_ALLOWED_USERS` | пользователи, чьи команды исполняются |
| `AGENT_LOG_LEVEL` | уровень логирования |

Команда `check-config` проверяет всё сразу и печатает полный список
недостающего, а не останавливается на первой проблеме.

## Аудит

Каждое действие сессии попадает в журнал, из которого восстанавливается
цепочка: хэш diff веток → хэш намерения → хэши промпта и ответа модели →
результат проверки → кто подтвердил план → ссылка на pull request →
дополнительные коммиты → кто подтвердил PR. Демонстрационный прогон печатает
эту цепочку в конце.

Инициатор сессии и подтвердившие записываются в тело pull request явным
текстом: на сервере коммиты создаются под технической учётной записью, и по
автору коммита участников не определить.

Секреты вырезаются из логов и журнала перед записью — известные значения
дословно, а типовые формы записи по шаблонам.
