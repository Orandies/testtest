## SourceControl API v3

✅ Источники: внутренний Swagger системы контроля версий и страница «API SourceControl»
на внутреннем портале документации.

- ✅ **Только v3.** v1 официально не поддерживается разработчиком — не рассматриваем вообще.
- ✅ **Точка входа — отдельный API-домен**, а не хост, на котором открывается Swagger.
  Значение `base_url` в конфигурации не совпадает с адресом, который виден в браузере.
- ✅ Покрытие тегов API под наши модули:

| Тег API | Наш модуль | Зачем |
|---|---|---|
| `compare` | Branch Diff Analyzer | diff релизной ветки к базовой |
| `files` | Branch Diff Analyzer + SourceControl | чтение и запись конфигов стендов |
| `branches` | SourceControl Module | временная ветка из релизной |
| `commits` | SourceControl Module | коммиты и доп. коммиты |
| `pulls` | SourceControl Module | pull request |
| `comments` | SourceControl Module | комментарии к PR |
| `repos` / `projects` | Оркестратор | список репозиториев для цикла |
| `privileges` | Оркестратор | проверка прав учётной записи |
| `branch_protections` | Validation | не защищена ли целевая ветка |

### ✅ Пути эндпоинтов

Server-префикс задаётся в `base_url`. **Репозиторий адресуется тройкой
`{tenant}/{project}/{repo}`**, а не одним именем — в коде это `RepoRef`.

| Тег | Метод и путь | Назначение |
|---|---|---|
| `projects` | `GET /tenants/{tenant}/projects` | список проектов тенанта |
| `branches` | `GET`/`POST` `/repos/{tenant}/{project}/{repo}/branches` | список / создание ветки |
| `branches` | `GET`/`DELETE` `…/branches/{branch_name}` | получить / удалить ветку |
| `files` | `GET …/raw/{path}` | **сырое содержимое файла** |
| `files` | `GET …/contents/{path}` | метаданные файла |
| `files` | `POST …/contents/file/create` · `PUT …/contents/file/update` · `POST …/contents/file/delete` | запись файлов (по одному!) |
| `pulls` | `GET`/`POST` `…/pulls` · `GET`/`PATCH` `…/pulls/{index}` | список / создание / чтение / правка PR |
| `pulls` | `GET …/pulls/{index}/commits` · `…/files` · `…/diff` · `…/issues` · `POST …/decline` | детали PR |
| `pulls` | `GET /tenants/{tenant}/pulls` | все PR тенанта |
| `comments` | `GET`/`POST` `…/pulls/{index}/comments` · `GET`/`PATCH`/`DELETE` `…/comments/{comment_id}` | комментарии PR |

- ✅ **PR адресуется порядковым номером `index`** в пределах репозитория, не глобальным id.
- ✅ **Запись файлов — пофайловая** (`contents/file/update`), «одного коммита на N файлов»
  в API нет: `commit_files()` применяет файлы по одному в порядке сортировки путей.
- ⚠️ **Операция слияния в API СУЩЕСТВУЕТ**, и мы её сознательно НЕ реализуем
  (незыблемый инвариант №3). Это ровно та причина, по которой инвариант записан:
  доступность операции в API не делает её частью агента.
- ❓ Схемы тел запросов и ответов (какие поля в body create_branch, update_file,
  create_pull) — разделы в Swagger не раскрывались; допущения помечены ❓ в клиенте.
- ✅ Fallback «локальный git clone + push» отменён — все операции есть в API.
- ✅ **Ветки репозитория конфигов:** постоянные `master` и `psi`, релизные вида
  `release/<версия>`. То есть **base для diff — это `master` или `psi`**; какую из двух
  брать за базу в конкретном релизе, задаёт инженер параметром сессии (вопрос №14).
  ⚠️ Имя релизной ветки в плане установки и в дереве веток может отличаться
  уточнением патч-версии — либо разные репозитории именуют по-разному, либо это тег
  (вопрос №16).
- ✅ **Стенд — это ФАЙЛ, а не ветка.** Репозиторий конфигов устроен так:

  ```
  agents/        по файлу на стенд
  common/        общий для всех стендов файл
  integrations/  тот же набор стендов
  namespace/     тот же набор стендов
  ```

  Три каталога содержат одинаковый набор стендов, `common/` — один общий файл.
  ⚠️ Расширения не единообразны: часть файлов `.yml`, часть `.yaml` — поиск файла
  по имени стенда должен учитывать оба варианта.
- ❓ Точный API-хост контура не подтверждён проверкой (вопрос №5).
- ❓ Аутентификация: нужна страница про API-ключ технической учётной записи (вопрос №4).
- ❓ Полный список репозиториев и правило «хаб → репозиторий» (вопрос №6): известен один.
- Реализация: тонкая httpx-обёртка, таймауты, 3 ретрая с backoff. `merge()` отсутствует физически.

## GigaChat

✅ Источники: внутренний регламент вывода в промышленную среду и документация
портала разработчика.

- ✅ Function calling официально поддерживается; ReAct — рекомендованная практика.
- ✅ SDK `gigachat`: контракт `client.chat.create()` / `stream()` / `parse()`;
  модели `ChatCompletionRequest`, `ChatMessage`, `ChatFunctionSpecification`, `ChatFunctionsTool`;
  встроенный mTLS (`cert_file` / `key_file` / `key_file_password`);
  встроенные ретраи (`max_retries`, `retry_backoff_factor`);
  контекстные `X-Session-ID` / `X-Request-ID` — связать с `session_id` FSM для аудита.
- ✅ Доступ: mTLS плюс регистрация в системе учёта обращений к модели и заявки на стенды.
- ✅ У модели только инструменты чтения, ноль инструментов записи.
- ❓ Выбор размера модели — решать по бенчмаркам и тестовой корзине.
- ❓ Обязателен ли внутренний реестр описаний функций для наших инструментов.
- ❓ SLA и латентность в контуре — замерить на тестовом стенде.
- Промпт-протокол (JSON в тексте) остаётся страховкой, если function calling подведёт.

## Чат-бот (основной интерфейс)

- ✅ Полноценный двусторонний bot API существует, релизы раз в две недели.
- ❓ **Блокер модуля `sberchat_bot/`:** механика доставки (webhook или long-polling),
  SDK, регистрация бота, команды, кнопки, лимиты. Без консультации модуль не пишем —
  ядро от этого не зависит.
- Требование безопасности: реагировать только на сообщения авторизованного инженера (allowlist).

### Fallback: одностороннее webhook-информирование

✅ Это НЕ bot API — только направление «система → чат».

| Endpoint | Body | Назначение |
|---|---|---|
| `GET webhooks/{token}/status` | — | проверка токена |
| `POST webhooks/{token}` | `{"text": "..."}` | текстовое оповещение в группу |
| `POST webhooks/file/{token}` | — | файл (⚠️ передача файлов пока не работает) |

- Токен генерирует владелец группы через клиент мессенджера, нужно отдельное право.
- Есть ограничение частоты с автоблокировкой учётной записи — шлём только PR и итог,
  не каждый шаг.
- Роль: резервный канал уведомлений, если bot API задержится. Итоговый отчёт — текстом
  со ссылками на PR, не файлом.

## Confluence (план установки)

- Клиент: atlassian-python-api — ❓ совместимость с внутренней версией.

### ✅ Структура страницы релиза

Одна страница — один релиз одной системы версии X.Y.

**Шапка страницы:**
- панель с подсказкой о том, что релиз выпущен, и чекбокс «Установлен»;
- панель со **списком хабов, на которые релиз установлен, сгруппированным по
  кластерам** (чекбоксы). Один хаб может присутствовать в нескольких кластерах,
  поэтому ключ позиции — пара «кластер и хаб». Конкретные имена хабов и кластеров
  читаются со страницы во время работы и в документацию не выносятся.

**Макрос `UI Expand` «Общая информация»** — восемь разделов: цели релиза; контакты
по релизу; инструкция по развёртыванию; тест-кейсы; план отката; проверки после
установки; риск внедрения; список потребителей.

⚠️ Раздел контактов содержит персональные данные. Агент их не читает и в промпт
модели не передаёт.

**Дальше — несколько макросов `UI Expand`, по одному на «поток» релиза.** Заголовок
потока перечисляет затронутые хабы и имя изменяемого сервиса. Внутри каждого потока
одинаковая структура:
- панель «Релиз» со ссылкой на задачу-эпик;
- панель «Информация» с датой передачи релиза на предпромышленный стенд;
- **заголовок «Deploy-plan/План установки» и таблица** — это и есть НАМЕРЕНИЕ;
- заголовок «Release notes» с таблицей «номер, задача, как было, как стало».

### ✅ Таблица «Deploy-plan/План установки» — источник НАМЕРЕНИЯ

Колонки: **задача, описание, предпромышленный стенд, промышленный стенд.**

- Задача — ссылка на задачу в трекере.
- Описание — что делать. Три наблюдаемых вида:
  1. **«Действия не требуются»** — большинство строк, конфиги не трогаем;
  2. **параметры в формате `KEY=value`**;
  3. **параметры в макросе «Блок кода» в формате `KEY: value`** (YAML-стиль).

  Плюс свободный текст-пояснение и иногда прямые ссылки на примеры конфигов.
- Колонки стендов — **не содержание изменений, а чек-лист исполнения**: применяли или
  нет, причина, дата, кто применил. Агент их читать может, но НАМЕРЕНИЕ берётся
  только из описания.

**Два вида плейсхолдеров в значениях — сами по себе не применимы, значение подставляет
человек** (вопрос №12):
- указание «подставить сюда адреса брокеров» — значение агенту неизвестно;
- шаблон вида `<префикс>_{ХАБ}` — значение зависит от хаба.

**Условное применение:** строка может начинаться с маркера охвата и применяться не ко
всем хабам потока. Формализованного признака нет, только текст → в модели НАМЕРЕНИЯ
это `comment` плюс низкий confidence, решает человек в цикле 1.

### ❓ Что осталось по плану установки

- Исходник страницы в storage format (XML) — по структуре всё ясно, но точные имена
  макросов и разметку таблиц надёжнее взять из XML (вопрос №2, остаток).
- Правило «строка плана установки → конкретный репозиторий и файл» (вопрос №13).
