# release_promotion_agent — Архитектура

> Основной интерфейс — бот в корпоративном мессенджере, двусторонний bot API подтверждён.
> Ядро транспорт-агностично: терминал и бот подключаются к оркестратору
> одинаковыми адаптерами, смена интерфейса ядро не затрагивает.

## Что делает агент

Автоматизирует ручной процесс инженера сопровождения при каждом релизе: обновление
конфигурационных файлов примерно восемнадцати контроллеров, разложенных по нескольким
репозиториям. Сейчас вручную: прочитать план установки в Confluence → руками править
конфиги → коммит → запрос на слияние → деплой штатным CI/CD.

Агент: **долгоживущий** Python-процесс (не разовая команда) в одном Docker-контейнере
на рабочей машине инженера, под его учётной записью. Модульный монолит.
Микросервисов нет by design.

## Бизнес-процесс (10 шагов, всё взаимодействие — в чате)

1. Инженер пишет боту параметры сессии: релиз, репозитории, стенды.
2. Агент снимает diff конфигов: релизная ветка ↔ базовая по каждому репозиторию
   (SourceControl API v3, тег `compare`). Это **ФАКТ** — что реально менялось в релизе.
3. Агент читает план установки из Confluence. Это **НАМЕРЕНИЕ** — что должно поменяться
   по инструкции.
4. Агент строит список изменений для конфигов целевых стендов (GigaChat, только
   read-only инструменты) и детерминированный отчёт расхождений ФАКТ ↔ НАМЕРЕНИЕ
   (Reconciliation).
5. **Цикл 1 — подтверждение плана.** Расхождения выводятся человеку. Инженер шлёт
   корректировки (агент пересчитывает через модель) или подтверждает. До подтверждения —
   строго только чтение.
6. Временная ветка создаётся копией из релизной.
7. Изменения коммитятся во временную ветку — **детерминированным Python-кодом**, не моделью.
8. Открывается pull request: временная ветка → релизная.
9. **Цикл 2 — ревью PR.** Инженер описывает правки сообщением → модель переводит
   текст правки в изменения файлов → агент делает доп. коммит → инженер проверяет.
   Подтверждено — дальше.
10. **Цикл по репозиториям:** шаги 6–9 повторяются для каждого репозитория
    последовательно. По завершении — итоговый отчёт со всеми PR. Слияние и деплой —
    вне агента.

## Компоненты и границы ответственности

| Модуль | Отвечает за | НЕ отвечает за |
|---|---|---|
| Интерфейс чат-бота | Диалог, сбор параметров, рендер плана, расхождений и PR, сбор решений в двух циклах, привязка чата к сессии FSM | Бизнес-логику анализа и записи |
| CLI (отладка) | Тот же сценарий через терминал для локальной отладки без чата | Ничего своего — тонкий адаптер |
| Оркестратор | Узкий ReAct-цикл, FSM, координация модулей, цикл по репозиториям | Прямые вызовы внешних API (только через модули) |
| Branch Diff Analyzer | Получение и нормализация diff релизной ветки к базовой по каждому репозиторию | Интерпретацию смысла изменений (это модель) |
| Deploy Plan Reader | Чтение и разбор плана установки в структуру | Интерпретацию бизнес-смысла |
| Reconciliation | Детерминированная сверка: что есть в diff, но нет в инструкции, и наоборот | Решение «кто прав» (это человек в цикле 1) |
| GigaChat Module | Промпты, вызовы модели (анализ, пересчёт, правки → изменения файлов), ретраи | Проверку корректности (не самопроверка) |
| Validation | Схема pydantic и контроль границ правок | Решение «применять или нет» (это человек) |
| SourceControl Module | Временная ветка, коммиты, PR, доп. коммиты; идемпотентные проверки | Слияние (физически не реализовано) |
| State Module | Состояние сессии и репозиториев в памяти процесса | Бизнес-логику |
| Audit Module | Структурированные JSON-события с редакцией секретов | Хранение секретов в открытом виде |

Все стрелки сходятся в оркестраторе (`agents/release_agent.py` в текущей ветке,
см. таблицу соответствия имён в [03_BACKLOG.md](03_BACKLOG.md)): только он вызывает
модули, модули друг друга напрямую не вызывают. Единственная прямая связка —
`llm → validation`: результат модели всегда проходит детерминированную проверку до
того, как его увидит оркестратор.

## Sequence — happy path (текстом)

Инженер → чат: параметры → Оркестратор: старт сессии (FSM) →
SourceControl: diff по каждому репозиторию → Confluence: план установки →
модель (read-only инструменты): план изменений и расхождения → чат: план человеку →
[Цикл 1: корректировки ↔ пересчёт] → подтверждение плана →
для каждого репозитория: временная ветка → коммит (детерминированный код) → PR →
чат: ссылка → [Цикл 2: правки текстом → модель → доп. коммит] → подтверждение PR →
следующий репозиторий → итоговый отчёт со всеми PR. Модель участвует три раза за
сессию (анализ, пересчёт, правки), всегда только на чтение. До подтверждения плана
к SourceControl идут только запросы чтения.

## Узкий ReAct-цикл — детально

**Почему узкий, а не открытый агент:** least privilege. Модель не получает ни одного
инструмента записи; запись выполняет только детерминированный Python после явного
подтверждения. Validation — детерминированная проверка, не ещё один вызов модели
(«проверяющий никогда не пишет код, который проверяет»).

**Инструменты чтения, доступные модели в релизном сценарии (целевое состояние):**

| Инструмент | Вход | Выход | Ошибки |
|---|---|---|---|
| `get_branch_diff(repo_id)` | id репозитория | нормализованный diff релизной ветки к базовой | REPO_UNAVAILABLE → расхождение помечается low-confidence |
| `get_deploy_plan_section(section_id)` | id раздела | текст релевантного раздела инструкции | NOT_FOUND → полный план с пометкой low-confidence |
| `get_current_config(repo_id, env)` | репозиторий и стенд | текущий конфиг из релизной ветки | FILE_MISSING → эскалация человеку |
| `get_reconciliation_report()` | — | детерминированный отчёт расхождений | — (готовится модулем Reconciliation) |
| `validate_config(candidate, repo_id, env)` | кандидат-файл | признак валидности, ошибки, предупреждения | никогда не «падает»: ошибка разбора — это первая запись в errors |
| `diff_against_current(candidate, repo_id, env)` | кандидат-файл | unified diff | — |

> Состояние на сегодня: этих инструментов в коде ещё нет. Модели сейчас доступны
> только два инструмента чтения Confluence, см. [05_STATUS.md](05_STATUS.md).

**Ретрай-протокол — 3 фазы, каждая даёт более специфичный фидбэк следующей попытке:**
формат → схема (pydantic) → границы плана.

**Условия остановки цикла:**
- Успех: проверка пройдена И diff не задевает файлы и ключи вне подтверждённого плана.
- Нужен человек: 3 неудачные попытки подряд → эскалация, инженер правит вручную.
- Застревание: идентичная ошибка на попытках 1 и 2 → сразу эскалация, без третьей попытки.
- Деградация: модель недоступна дольше порога → инженер получает сырой diff и
  инструкцию, пайплайн не блокируется.

**Параллелизм:** анализ diff по репозиториям можно распараллелить (только чтение);
запись — строго последовательно, по одному репозиторию, каждая под своим подтверждением.

## FSM сессии

```
[*] → SESSION_STARTED → PARAMS_COLLECTED → DIFF_ANALYZED → PLAN_ANALYZED → PLAN_PROPOSED
PLAN_PROPOSED → AWAITING_PLAN_APPROVAL
AWAITING_PLAN_APPROVAL → PLAN_CORRECTION → PLAN_PROPOSED   (корректировки → пересчёт)
AWAITING_PLAN_APPROVAL → PLAN_APPROVED                     (подтверждение)
PLAN_APPROVED → REPO_BRANCHING → REPO_COMMITTED → PR_OPENED → AWAITING_PR_APPROVAL
AWAITING_PR_APPROVAL → PR_CORRECTION → AWAITING_PR_APPROVAL (правки → доп. коммит)
AWAITING_PR_APPROVAL → REPO_DONE
REPO_DONE → REPO_BRANCHING (есть ещё репозитории) | ALL_DONE → [*]
```
Состояния AWAITING_* живут в памяти процесса: сессия может стоять часами, но перезапуск
её не переживает — начинать придётся заново. Постоянное хранилище сознательно отложено,
решение о нём принимается отдельно. Ошибки внешних вызовов обрабатываются ретраями
внутри операций и в главную FSM не выносятся.

## Обработка ошибок

| Внешний вызов | Отказ | Поведение агента |
|---|---|---|
| SourceControl недоступен (diff) | Этап анализа | 3 ретрая с backoff → сообщение в чат, сессия сохраняется, продолжение командой инженера |
| Confluence недоступен | Этап анализа | 3 ретрая с backoff → сообщение в чат; опция: продолжить только по diff с пометкой «инструкция недоступна» |
| Модель вернула невалидный ответ | Любая фаза проверки | До 3 попыток с прогрессивным фидбэком → эскалация с последним кандидатом |
| Модель недоступна дольше порога | Анализ или правки | Деградация: сырой diff и инструкция инженеру, агент не блокирует |
| SourceControl отказал в ветке или коммите | Цикл по репозиториям | Ветка от этой сессии переиспользуется; иначе эскалация, ручной разбор; остальные репозитории не блокируются |
| SourceControl отказал в PR | Цикл по репозиториям | Проверка существующего PR по паре «сессия и репозиторий» — переиспользовать или создать |
| Чат недоступен | Любой момент | Досылка последнего сообщения сессии при восстановлении; резервный канал для финального отчёта |
| Процесс перезапущен | Любой момент | Сессия теряется, начинается заново: постоянного хранилища пока нет |

## Безопасность и аудит

- Токены (Confluence, SourceControl, модель, бот) — из внутренней системы управления
  секретами (этап 2; локально `.env`), инъекция как переменные окружения при старте.
  Не в образе, не в репозитории, не в логах.
- Доступ к модели — по mTLS (SDK нативно: `cert_file` / `key_file`) плюс регистрация
  и заявки на стенды.
- Проверка наличия всех секретов — первым шагом, до любого сетевого вызова (fail-fast).
- Ни один секрет не попадает в промпт модели; фильтр по шаблонам на случай секретов
  в конфигах и diff.
- Токен SourceControl — только чтение и создание ветки, коммита, PR, без слияния и
  административных прав; дублируется отсутствием `merge()` в клиенте (defense in depth).
- Команды из чата — только от авторизованного инженера (allowlist); чужие сообщения
  игнорируются.
- Цепочка аудита: diff_hash → plan_hash → prompt_hash → response_hash → результат
  проверки → кто подтвердил план → ссылка на PR → доп. коммиты → кто подтвердил PR.

## Наблюдаемость (MVP, облегчённая)

Метрики считаются по журналу аудита: время сессии, число итераций циклов 1 и 2, доля PR
без доп. коммитов, попытки на репозиторий. Отчёт по сессии — командой в чате или
в терминале. Логи JSON, ротация по размеру, хранение 30 дней.

## Эволюция: рабочая машина → сервер. Восемь швов с первого коммита

1. `user_id` и `session_id` в каждой записи журнала и в каждом объекте состояния.
2. Ноль глобальных переменных — SessionContext передаётся явно параметром.
3. Работа с состоянием — через интерфейс хранилища, а не напрямую: подменить память
   на постоянное хранилище можно будет одной реализацией.
4. Секреты только из окружения: локально `.env`, на сервере — внутренняя система
   управления секретами; код не меняется.
5. Инициатор и подтвердившие явно в тело PR и в журнал аудита (на сервере автор
   коммита — техническая учётная запись).
6. Allowlist «кому можно запускать» — даже с одной записью.
7. Логи только JSON, в каждой записи session_id и user_id — уедут в систему сбора
   логов как есть.
8. Тестовая корзина с первого дня — для валидации: пары «diff и план установки →
   эталонный план».

**Отложено сознательно** (стоит одинаково сейчас и потом): постоянное хранилище и
СУБД, оркестрация контейнеров, веб-интерфейс, разграничение прав, отказоустойчивость,
метрики, разделение на сервисы.

**Учётная запись — главная засада при переезде на сервер:** на рабочей машине коммиты
подписаны инженером, на сервере — технической учётной записью. Поэтому правило №5
(явная запись инициатора и подтвердивших) — с первого дня.

## Путь в промышленную среду

1. Среда разработки: рабочая машина инженера сопровождения, Docker, локальный клон
   репозитория.
2. Окружение и модель: mTLS-сертификат, регистрация, заявки на стенды, система
   управления секретами.
3. Исследование и проектирование: ReAct — рекомендованная практика.
4. Разработка: Python 3.11+, SDK модели, зависимости только из внутреннего зеркала.
5. Выходные артефакты: Docker-образ, внутренний репозиторий артефактов, CI, тестовая
   корзина.
6. Валидация модели по внутренней процедуре: карточка в реестре моделей и отчёт
   о разработке (контакты — у владельцев процесса).
7. Вывод в промышленную среду.
