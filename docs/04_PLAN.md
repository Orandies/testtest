## Что агент делает

Автоматизирует то, что инженер сопровождения делает руками при каждом релизе:
обновление конфигов примерно восемнадцати контроллеров по нескольким
репозиториям. Опирается на два независимых источника и не смешивает их:

- **ФАКТ** — diff релизной ветки к базовой, что реально изменилось;
- **НАМЕРЕНИЕ** — план установки со страницы релиза, что должно измениться.

Расхождения между ними выносятся человеку. После подтверждения плана агент
готовит ветку и коммит и останавливается на pull request. Слияние и деплой —
всегда вне агента, штатным процессом.

## Принятое направление: сначала локальный режим

Агент работает с **локальным клоном репозитория конфигов**, а не через
SourceControl API. Читает diff и файлы командами `git`, готовит ветку и коммит
там же, останавливается и отдаёт инженеру команду для отправки и ссылку для
создания pull request. На сервер при этом не уходит ничего.

Это снимает три открытых вопроса разом — №4 (аутентификация), №5 (хост контура)
и №15 (значение tenant). Ни один из них локальному git не нужен, и ждать
доступов, чтобы начать работать на реальных конфигах, не придётся.

Архитектуру это не меняет. В оркестраторе система контроля версий приходит
интерфейсом `SourceControlPort`, у которого уже две реализации — клиент API и
заглушка для прогона без сети. Локальный git будет третьей. Оркестратор,
анализаторы, валидация и аудит не трогаются.

## Постоянное хранилище отложено

Состояние сессии живёт в памяти процесса. Сессия может висеть часами в ожидании
подтверждения, но перезапуск её не переживает — начинать придётся заново.

Это осознанное решение, а не недоделка: пока сценарий обкатывается на одной
машине, хранилище добавляет работы и ничего не доказывает. Работа с состоянием
идёт через интерфейс, поэтому подключить постоянное хранилище можно будет одной
реализацией, не трогая оркестратор. Вернёмся к этому, когда сессии станут
длинными настолько, что терять их будет дорого.

## Этапы

### Этап 1. Локальный git — ничем не заблокирован

- `tools/local_git.py`: реализация `SourceControlPort` поверх команд `git`.
- Работа во временном `git worktree`: рабочий каталог инженера не трогается.
- Соответствие «репозиторий → каталог клона» задаётся параметрами сессии,
  а не зашивается в код.
- Тесты на настоящем временном репозитории, заглушки не нужны — git создаст всё сам.
- Выбор реализации в терминале: локальный git по умолчанию, API — когда
  появятся доступы.

**Что даёт:** первый прогон на реальном репозитории конфигов.

**Открытый вопрос к этапу:** останавливается ли агент на готовой локальной ветке,
отдавая инженеру команду отправки и ссылку на создание pull request, — или сам
отправляет ветку под учётными данными инженера после подтверждения плана.
Первое безопаснее: на сервер не уходит ничего.

### Этап 2. Разбор плана установки — частично заблокирован вопросом №2

- `analyzers/deploy_plan.py`: разбор страницы релиза в модель намерения.
- Структура разделов уже описана в [02_INTEGRATIONS.md](02_INTEGRATIONS.md)
  по реальной странице релиза.
- Остаток вопроса №2: исходник страницы, чтобы знать точные имена макросов.
- Сюда же вопросы №12 (плейсхолдеры вида «указать здесь серверы кафки») и
  №13 (правило «строка плана → репозиторий и файл»).

**Что даёт:** намерение читается со страницы, а не задаётся руками.

### Этап 3. Подключение модели к релизному сценарию

- Шесть read-only инструментов и промпты в `llm/`.
- У модели по-прежнему ноль инструментов записи: ветку и коммит делает
  обычный код после подтверждения человеком.
- Ретрай-протокол из трёх фаз: формат → схема → границы плана.

**Заблокирован** этапом 2: без разбора плана модели нечего подавать.

### Этап 4. Бот в Сберчате — заблокирован вопросом №1

- `sberchat_bot/` как второй адаптер к тому же оркестратору.
- Ядро транспорт-агностично: терминал уже работает через тот же интерфейс,
  ядро при подключении бота не меняется.

### Этап 5. Живые вызовы SourceControl API

- Включается, когда появятся токен, хост и значение tenant.
- Код клиента написан и покрыт тестами на заглушках, переписывать не придётся.

### Отложено сознательно

Постоянное хранилище сессий, Postgres, Kubernetes, веб-интерфейс, разграничение
прав, отказоустойчивость, разделение на сервисы. Стоят одинаково сейчас и потом,
поэтому делаются тогда, когда понадобятся.
