# Модули и классы

> Карта кода: где что лежит и за что отвечает. Подробности — в описаниях
> самих классов, здесь только назначение и связи между ними.
> Архитектура — [01_ARCHITECTURE.md](01_ARCHITECTURE.md).

## Как устроен пакет

Слоями. Внизу `core` — он не знает ни о ком. Над ним анализ и проверка,
они не знают друг о друге. Выше `tools` — единственное место, которое
ходит по сети. Всё связывает оркестратор: модули друг друга не вызывают,
и это проверяется линтером, а не договорённостью.

```
cli · sberchat_bot          интерфейсы
        │
     agents                 оркестратор релиза и диалоговый агент
        │
analyzers · tools · llm     анализ · внешние системы · модель
        │
   validation               детерминированная проверка
        │
      core                  автомат, состояние, ошибки, аудит, логи
```

## core — фундамент

Автомат сессии, её состояние, ошибки, аудит и логи. Ни от кого не зависит:
всё, что здесь лежит, можно читать, не зная остального кода.

Состояние живёт в `SessionStore`, а `SessionFSM` только проверяет переходы
по таблице и записывает их. Поэтому у сессии одна точка правды и один
журнал, и по журналу восстанавливается весь её путь, а не только текущее
положение.

| Класс | Файл | Назначение |
|---|---|---|
| `SessionState` | `core/fsm.py` | Состояния сессии от старта до завершения |
| `RepoState` | `core/fsm.py` | Состояние отдельного репозитория в цикле |
| `SessionFSM` | `core/fsm.py` | Проверяет переход по таблице и записывает его |
| `SessionContext` | `core/context.py` | Кто запустил, какой релиз, с какими параметрами |
| `SessionStore` | `core/session.py` | Всё состояние одной сессии в одном объекте |
| `RepoTask` | `core/session.py` | Состояние репозитория; одна запись на репозиторий за сессию |
| `PlanItem` | `core/session.py` | Позиция плана: совпадение или расхождение |
| `Approval` | `core/session.py` | Решение инженера на чекпоинте |
| `LlmCall` | `core/session.py` | Вызов модели: хэши, попытки, итог проверки |
| `AuditEvent` | `core/session.py` | Событие журнала, уже без секретов |
| `RepoAuditChain` | `core/audit_chain.py` | Цепочка «на каком основании изменился конфиг» |
| `Redactor` | `core/redaction.py` | Вырезает секреты до записи в журнал |
| `JsonFormatter` | `core/logging_setup.py` | Запись лога → строка JSON без секретов |
| `AgentError` и наследники | `core/errors.py` | Восемь видов отказов агента |

**Что стоит знать.** `Redactor` работает в два слоя: известные значения
вырезаются дословно, типовые формы записи — по шаблонам, на случай
секретов, о которых агент не знает. Известные значения обрабатываются от
длинного к короткому, иначе короткий разорвал бы длинный и остаток ушёл бы
в лог открытым текстом.

## analyzers — два источника и их сверка

Здесь появляются ФАКТ и НАМЕРЕНИЕ и здесь же они сверяются. Всё
детерминированно: одинаковый вход даёт побайтово одинаковый выход и
одинаковый хэш. Это нужно и для аудита, и для тестовой корзины.

| Класс | Файл | Назначение |
|---|---|---|
| `BranchDiff` | `analyzers/branch_diff.py` | ФАКТ: что изменилось в релизной ветке |
| `FileDiff` | `analyzers/branch_diff.py` | Изменения в одном файле; ошибка разбора не молчит |
| `KeyChange` | `analyzers/branch_diff.py` | Изменение одного ключа, путь через точку |
| `ChangeKind`, `FileStatus` | `analyzers/branch_diff.py` | Что случилось с ключом и с файлом |
| `ChangedFileInput` | `analyzers/branch_diff.py` | Один файл в двух версиях, на вход разбора |
| `ReleaseIntent` | `analyzers/intent.py` | НАМЕРЕНИЕ: что должно измениться по инструкции |
| `IntentChange` | `analyzers/intent.py` | Одна позиция инструкции |
| `ReconciliationReport` | `analyzers/reconciliation.py` | Что совпало и что разошлось |
| `Discrepancy`, `MatchedItem` | `analyzers/reconciliation.py` | Одно расхождение и одно совпадение |
| `DiscrepancyKind` | `analyzers/reconciliation.py` | Четыре вида расхождений |

**Что стоит знать.** Список в конфиге считается одним значением целиком, а
не набором элементов: порядок в конфигах контроллеров значим. Файл, который
не разобрался как YAML, не пропускается — он уходит человеку отдельным
расхождением, потому что сверить его по ключам невозможно.

Отчёт ничего не решает. Выбирать, какой источник правильный, агент не
имеет права: источники расходятся не только когда кто-то ошибся.

## validation — детерминированная проверка

Проверяет то, что предложила модель, и не зависит ни от кого: ни от
анализаторов, ни от модели, ни от системы контроля версий. Это не
формальность — проверяющий код не должен зависеть от кода, чьи результаты
он проверяет. Запрет закреплён контрактом линтера.

| Класс | Файл | Назначение |
|---|---|---|
| `CandidateFile` | `validation/models.py` | Кандидат на запись: содержимое, предложенное моделью |
| `ValidationResult` | `validation/models.py` | Признак успеха, ошибки и предупреждения |
| `Env` | `validation/models.py` | Стенды, для которых готовятся изменения |

**Что стоит знать.** Проверка никогда не бросает исключение: ошибка разбора
YAML — это тоже результат, она попадает в `errors`. Модель должна получить
то, с чем можно работать на следующей попытке, а не аварию.

Вторая половина модуля — контроль границ плана: правка, задевшая файл или
ключ вне подтверждённого плана, отклоняется. Не предупреждение, а отказ.

## agents — оркестратор и диалог

Два входа в систему. `Orchestrator` ведёт релизный сценарий, `ChatAgent`
отвечает на вопросы текстом и ничего не меняет.

Оркестратор — единственное место, которое знает порядок шагов целиком.
Три внешние зависимости приходят интерфейсами и подменяются целиком:
система контроля версий, источник плана и канал общения с инженером. На
этом шве работает и прогон без сети, и будущий локальный режим.

| Класс | Файл | Назначение |
|---|---|---|
| `Orchestrator` | `agents/release_agent.py` | Ведёт сессию от параметров до открытых PR |
| `SourceControlPort` | `agents/release_agent.py` | Интерфейс системы контроля версий. Слияния в нём нет |
| `PlanEngine` | `agents/release_agent.py` | Интерфейс источника плана: предложить, пересчитать, поправить |
| `HumanInterface` | `agents/release_agent.py` | Интерфейс инженера: показать план и PR, получить решение |
| `SessionParams`, `RepoParams` | `agents/release_agent.py` | Параметры запуска и координаты репозитория |
| `ProposedPlan` | `agents/release_agent.py` | План от модели с хэшами промпта и ответа |
| `PlannedFileChange` | `agents/release_agent.py` | Кандидат и границы допустимых правок для него |
| `Decision` | `agents/release_agent.py` | Подтверждение либо текст корректировки |
| `SessionResult` | `agents/release_agent.py` | Итог: конечное состояние и ссылки на PR |
| `ChatAgent` | `agents/chat_agent.py` | Диалог с моделью, чтение страницы по ссылке |

**Что стоит знать.** До подтверждения плана не делается ни одной записи —
всё, что было раньше, только читало. Записывает всегда обычный код
оркестратора, а не модель: она лишь предлагает содержимое файлов.

## tools — выходы во внешние системы

Единственный слой, который ходит по сети. Пакет подгружает инструменты по
требованию: работа с системой контроля версий не тянет за собой Confluence
и всю его цепочку зависимостей.

| Класс | Файл | Назначение |
|---|---|---|
| `SourceControlClient` | `tools/git_tool.py` | Ветки, файлы, коммиты, pull request по HTTP API |
| `RepoRef` | `tools/models.py` | Координаты репозитория, из них строится путь API |
| `CompareResult`, `CompareFile` | `tools/models.py` | Ответ сравнения двух веток |
| `BranchInfo`, `PullRequestInfo`, `RepoInfo` | `tools/models.py` | Ответы API по ветке, PR и репозиторию |
| `FileChangeStatus` | `tools/models.py` | Что случилось с файлом, по данным API |
| `ConfluenceClient` | `tools/confluence_tool.py` | Чтение страниц: по идентификатору, заголовку, поиском |
| `ConfluencePage` | `tools/confluence_tool.py` | Прочитанная страница: HTML и текст |
| `DeployPlan`, `DeployPlanChange` | `tools/confluence_tool.py` | Разобранный план установки и его позиции |
| `ConfluenceReadError` | `tools/confluence_tool.py` | Страница не прочитана |

**Что стоит знать.** Метода слияния в `SourceControlClient` нет и не будет:
агент готовит изменения, но не вливает их. Это второй эшелон защиты к
токену без прав на слияние, и отсутствие метода закреплено тестом.

Сетевой протокол клиента: три попытки с растущей паузой на сетевых сбоях и
кодах 429 и 5xx; остальные ответы 4xx возвращают ошибку сразу — повторять
запрос с неверным токеном бессмысленно.

В Confluence агент только читает. Менять источник, по которому сам же
сверяешься, нельзя.

## llm, prompts, models — работа с моделью

Клиент, история переписки и системный промпт. Промпт собран из четырёх
частей: роль, правила, возможности, манера разговора. Разделение не
косметическое — правила меняются редко и требуют внимания, манера
правится часто, и правка одного не задевает другое.

| Класс | Файл | Назначение |
|---|---|---|
| `GigaChatClient` | `llm/gigachat_client.py` | Два режима аутентификации: взаимная TLS и токен |
| `ConversationManager` | `llm/conversation.py` | История переписки, уходит модели при каждом запросе |
| `SessionManager` | `llm/session.py` | Идентификатор сессии модели для аудита |
| `ChatResponse` | `models/chat_response.py` | Ответ модели: текст и расход токенов |
| `UsageStats` | `models/usage.py` | Расход токенов на один запрос |

**Что стоит знать.** Модель не помнит прошлые обращения сама — контекст
создаёт именно история переписки. Обрезки по длине пока нет: в длинном
диалоге история растёт, а вместе с ней расход токенов на каждом запросе.

Шести read-only инструментов релизного сценария здесь пока нет — это
следующий этап, см. [04_PLAN.md](04_PLAN.md).

## cli — терминал

Три команды: `check-config` показывает, что настроено и чего не хватает,
`demo` проходит сценарий целиком на заглушках без сети, `chat` открывает
диалог с моделью.

| Класс | Файл | Назначение |
|---|---|---|
| `InMemorySourceControl` | `cli/demo.py` | Репозиторий в памяти вместо настоящего |
| `ScriptedEngine` | `cli/demo.py` | Модель-заглушка с заранее заданным планом |
| `ScriptedHuman` | `cli/demo.py` | Инженер-заглушка с заранее заданными решениями |

**Что стоит знать.** Заглушки реализуют те же интерфейсы, что и настоящие
реализации, поэтому оркестратор не замечает подмены. Это же и есть
доказательство, что швы работают: если бы модули были связаны напрямую,
прогон без сети был бы невозможен.

## config.py — конфигурация

| Класс | Назначение |
|---|---|
| `Config` | Проверенная конфигурация, собирается один раз и дальше не меняется |

**Что стоит знать.** Секреты лежат в `SecretStr`: печать конфигурации в лог
их не раскрывает. Наружу значения отдаются только методом `secret_values` —
им пользуется фильтр логов, чтобы знать, что вырезать.

Обязателен ровно один пункт: режим аутентификации модели. Доступы к системе
контроля версий и Confluence нужны только релизному сценарию и проверяются
перед первым обращением к ним, а не при старте, — иначе инженера не пускало
бы в диалог из-за доступов, которые ему там не нужны.
