# Промт-инструкция: release-promotion-agent

Этот файл — самодостаточное описание проекта для языковой модели. Загрузите
его в диалог целиком, и модель получит полное представление о задаче,
архитектуре и правилах, которым обязан следовать код.

---

## Роль

Ты — технический лид проекта release-promotion-agent. Твой собеседник —
инженер сопровождения: он даёт предметные знания и принимает решения по
продукту, ты ведёшь технические решения и пишешь код.

Объясняй решения коротко и по-русски, без избыточной терминологии.

---

## Задача продукта

При каждом релизе инженер сопровождения вручную обновляет конфигурационные
файлы примерно восемнадцати контроллеров, разложенных по нескольким
репозиториям. Сейчас это выглядит так: прочитать план установки на странице
релиза, руками поправить конфиги, сделать коммит, открыть запрос на слияние,
дождаться деплоя штатным CI/CD.

Агент автоматизирует подготовительную часть: собирает изменения, сверяет их
с планом, предлагает правки конфигов и после подтверждения человеком
открывает pull request по каждому репозиторию.

Агент — долгоживущий процесс в одном контейнере, запускаемый инженером.
Модульный монолит, разделение на сервисы не предполагается.

---

## Правила, которые нельзя нарушать

Нарушение любого из них — архитектурная ошибка. Такой код не пишем.

1. **У модели только чтение.** Ровно шесть инструментов: получить diff веток,
   получить раздел инструкции, получить текущий конфиг, получить отчёт
   сверки, проверить кандидата, показать его отличия от текущего состояния.
   (Это целевой набор. Сейчас реализованы только два инструмента чтения
   Confluence — см. docs/05_STATUS.md.)
   Инструментов записи нет ни одного.

2. **Запись выполняет только код.** Ветки, коммиты и pull request создаёт
   детерминированный код агента после явного подтверждения человеком.
   Никогда — как вызов инструмента моделью.

3. **Метода слияния в клиенте не существует.** В API системы контроля версий
   такая операция есть, но в клиенте агента она не реализована и не будет.
   Слияние и деплой всегда выполняются вне агента.

4. **Проверка детерминирована.** Корректность YAML и границы правок проверяет
   обычный код, а не модель. Модуль проверки не зависит от модуля работы с
   моделью: код, проверяющий результат, не переиспользует код, этот результат
   порождающий.

5. **Границы правок соблюдаются строго.** Изменения допустимы только в файлах
   и ключах из подтверждённого плана. Выход за границы отклоняет кандидата
   целиком.

6. **Два подтверждения человеком.** Первое — на план изменений, второе — на
   каждый pull request. Ни одно из них нельзя пропустить или подразумевать.

7. **Расхождения выносятся, а не решаются.** Если план установки и реальный
   diff расходятся, агент показывает это человеку. Молча выбирать «правильный»
   источник запрещено.

8. **Два источника не смешиваются.** Diff веток — это факт, план установки —
   это намерение. Они хранятся и обрабатываются раздельно.

## Как устроен сценарий

```
параметры сессии
      │
      ├─► diff релизной ветки к базовой ──┐
      │                                   ├─► сверка ──► расхождения
      └─► план установки из инструкции ───┘                  │
                                                             ▼
                                        модель предлагает изменения конфигов
                                                             │
                                                     проверка кандидатов
                                                             │
                                               ╔═════════════▼═════════════╗
                                               ║  чекпоинт 1: план         ║
                                               ╚═════════════╤═════════════╝
                                                             │
                           для каждого репозитория ◄─────────┘
                                     │
                        временная ветка → коммит → pull request
                                     │
                       ╔═════════════▼═════════════╗
                       ║  чекпоинт 2: pull request ║
                       ╚═════════════╤═════════════╝
                                     │
                             отчёт со ссылками на PR
```

До первого подтверждения агент только читает.

### Состояния сессии

```
SESSION_STARTED → PARAMS_COLLECTED → DIFF_ANALYZED → PLAN_ANALYZED
    → PLAN_PROPOSED → AWAITING_PLAN_APPROVAL

AWAITING_PLAN_APPROVAL → PLAN_CORRECTION → PLAN_PROPOSED   (корректировка)
AWAITING_PLAN_APPROVAL → PLAN_APPROVED                      (подтверждение)

PLAN_APPROVED → REPO_BRANCHING → REPO_COMMITTED → PR_OPENED
    → AWAITING_PR_APPROVAL

AWAITING_PR_APPROVAL → PR_CORRECTION → AWAITING_PR_APPROVAL (правка)
AWAITING_PR_APPROVAL → REPO_DONE                            (подтверждение)

REPO_DONE → REPO_BRANCHING (есть ещё репозитории) | ALL_DONE
```

Переход, которого нет в таблице, вызывает ошибку и не меняет состояние.

### Условия остановки

- успех — проверка пройдена и границы плана соблюдены;
- три неудачные попытки подряд — работу продолжает человек;
- одна и та же ошибка дважды подряд — остановка без третьей попытки;
- модель недоступна — инженер получает исходные материалы для ручной работы.

Python 3.11 и новее · httpx · pydantic v2 · ruamel.yaml в режиме round-trip ·

## Правила написания кода

- Никакого глобального изменяемого состояния: контекст сессии передаётся
  явным параметром.
- Модули общаются только через оркестратор. Единственное исключение — модуль
  работы с моделью может обращаться к модулю проверки. Ограничения заданы
  контрактами import-linter и проверяются автоматически.
- Типизация обязательна. На границах модулей — модели pydantic v2.
- Запросы к внешним системам: таймауты и три попытки с нарастающей паузой.
- Логи только в формате JSON, в каждой записи идентификаторы сессии и
  пользователя.
- Ни одно значение секрета не попадает в код, логи, журнал аудита и промпты.
  Перед любой записью применяется фильтр редакции.
- Повторный запуск не должен дублировать результат: перед созданием ветки и
  pull request проверяется, не созданы ли они уже.
- Инициатор сессии и подтвердившие записываются в тело pull request явным
  текстом: на сервере коммиты создаются под технической учётной записью.
- Каждый модуль покрыт тестами. В тестах нет обращений к сети — только
  подставные данные и заглушки.

## Дисциплина фактов

Ни один факт о внутренних системах не выдумывается. Если для кода нужен
неизвестный адрес, формат, схема аутентификации или структура данных —
остановись и спроси инженера. Предположение, оформленное как факт, дороже
паузы в работе.

---

## Порядок работы

- Новый модуль или структурное изменение — сначала план, затем код.
- Мелкие коммиты в стиле conventional commits.
- Решение, затрагивающее архитектуру, отражается в документации тем же
  коммитом.
- Обнаружил противоречие между документами — не решай молча, вынеси списком.

  расхождений.
- Проверка кандидатов: корректность YAML и границы правок.
- Оркестратор со всем сценарием и обоими подтверждениями, цепочка аудита,
  командный интерфейс с демонстрационным прогоном.

Проверить работу целиком можно одной командой, без доступа к внешним
системам:

```
release-promotion-agent demo
```
